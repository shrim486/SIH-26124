# Public transport camera connection

Fleet monitoring now has an authenticated camera preview. No transport camera is connected in the local project yet. A registered camera becomes **Live** only while its actual preview frames are arriving and were captured within 15 seconds. Refreshing the page or registering a camera does not make it live.

## Connection path

1. A vehicle's authorised RTSP/HTTP camera feed, or USB camera, connects to its on-board edge computer.
2. The edge connector continuously reads that feed and sends a reduced JPEG preview to the API every two seconds over the vehicle's internet connection. It retains the newest frame while inference/upload runs, rather than accumulating a queue of old frames.
3. Government fleet monitoring reads the protected preview. It labels stopped frames as last received and supports pausing, resuming and selecting cameras. Only the latest preview per camera is retained.
4. GPS is sent separately from a GPS device. Registration alone supplies no coordinates and no moving vehicle markers.

This is a periodically refreshed live preview, not a full-frame-rate video stream or recording archive. Camera credentials stay on the edge device; the backend does not open arbitrary camera URLs. Preview images require government authentication and are not exposed to the public portal.

## Connect a camera

In the government portal, register the vehicle, then its camera. Select that vehicle and expand **Connect this camera** to get the correct camera ID. Set the camera's configured status to active.

On the edge device, install the project dependencies and create the ignored local file `edge_ai/.env.camera`:

```dotenv
URBANIQ_API_BASE=http://127.0.0.1:8000/api/v1
URBANIQ_CAMERA_SOURCE=rtsp://CAMERA_HOST/STREAM_PATH
URBANIQ_USERNAME=YOUR_GOVERNMENT_USERNAME
URBANIQ_PASSWORD=YOUR_GOVERNMENT_PASSWORD
```

Use `0` as the source for a connected USB camera. Local video files are deliberately rejected as live inputs. Replace the API address with the server reachable from the vehicle; `127.0.0.1` only reaches the edge computer itself. Use HTTPS for remote camera uploads. The current connector uses the project's government authentication; keep this credential file private.

Run from the project root, replacing the camera ID with the one registered in the portal:

```powershell
python -m edge_ai.live_camera --camera-id 1
```

To draw learned pothole boxes on the preview, use the installed pothole ONNX weights:

```powershell
python -m edge_ai.live_camera --camera-id 1 --pothole --conf 0.4
```

The model preview can miss hazards or produce false positives. This connector currently supports optional pothole annotations; the other models remain in the existing recorded-video analysis suite. It does not automatically create incident alerts or recorded evidence. Continue using the existing analysis/publication workflow to attach a recording and detected frames to an issue. No pretend vehicle data or incident positions are generated by the connector.

## Device GPS

An actual GPS integration can atomically write a JSON file and set `URBANIQ_GPS_FILE` to its path. The connector accepts finite coordinates and a timezone-aware fix timestamp no older than 30 seconds. It sends each new fix once with `source: device`; it does not replace missing GPS with camera or assigned map coordinates.

The file has `latitude`, `longitude` and ISO `recorded_at` fields. Values must come from the receiver. Camera timestamps represent when the edge computer receives a decoded frame; they cannot establish the upstream camera's clock or eliminate latency already inside its RTSP stream.

## APIs and retention

- `POST /api/v1/government/fleet/cameras/{id}/frame`: `captured_at`, `jpeg_base64`, optional `processing: raw|pothole`. Authenticated; registered active camera only; recent timezone-aware timestamp; maximum 512 KiB JPEG and 1920×1080 pixels. Images are decoded and re-encoded without embedded metadata. Older and duplicate frames are rejected.
- `GET` on the same endpoint: protected latest JPEG, `Cache-Control: no-store`, `X-Captured-At`, `X-Received-At`, `X-Frame-Processing`. No stored frame returns 404.
- Fleet responses include preview availability, capture time and live status; heartbeat health and device GPS remain separate.
- The `camera_frames` table stores one image per camera, replacing the previous image transactionally. It is not an evidence archive. API startup creates this table without deleting existing records.

## Route-planning alerts

The planner now loads the same active-record catalogue as both portal maps before a trip is planned. It refreshes every 15 seconds, supports fitting all alerts, and offers incident details from each marker. All active alerts are shown by default; after comparison, users can filter to the selected route. Resolved alerts disappear on refresh. If alerts change after a route was calculated, the page asks for another comparison.

Assigned positions remain visibly distinguished and excluded from scoring unless the user selects the existing inclusion option. A visible alert does not necessarily affect route ranking: report age, location provenance, proximity and whether it is an actual road obstruction determine that separately.

## Checks

`node scripts/check_fleet_render.mjs` renders the initial fleet/planner and camera waiting states, with map components stubbed. It also checks route-alert visibility and resolved-alert removal. `node scripts/check_portal_imports.mjs` checks actual Vite-served module imports in both running portals. These checks do not replace browser interaction tests.

Backend tests in `tests/test_live_cameras.py` cover preview authentication, image/time validation, replacement, duplicate rejection, freshness and camera status. Edge tests in `edge_ai/tests/test_live_camera.py` cover camera-source validation, actual-GPS requirements and preview encoding. Hardware capture still requires a connected camera to verify on the target device.
